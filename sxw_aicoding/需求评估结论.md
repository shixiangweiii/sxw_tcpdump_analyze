# tcpdump 结果分析工具 — 需求评估与方案结论

> 整理日期：2026-08-21
> 状态：评估完成，待开工

## 一、背景与动机

- Wireshark 太专业、太复杂，对新手不友好：界面信息过载、过滤语法门槛高，新手抓完包不知道看什么。
- tcpdump 的文本输出更难读。
- "抓了包但看不出问题"是新手普遍困境，市场上缺少"小白友好"的成品工具。

## 二、核心定位（关键结论）

**不做"简化版 Wireshark"，做"自动诊断报告生成器"。**

- Wireshark 复杂不是因为做坏了，而是网络本身复杂。做全功能简化版会陷入同样的坑。
- 差异化在于**场景化自动解读**：用户丢进一个 pcap，直接告诉他结论，用大白话解释问题。
- 成功关键在"自动给出人话结论"，而不是功能多少。

示例输出：

- 发现 3 次 TCP 重传集中在 10:32:15 前后，可能是网络抖动
- 这条 HTTP 请求耗时 2.3s，其中 1.8s 在等服务端响应
- 192.168.1.5 发起了 200 个连接，疑似端口扫描

## 三、已确定的产品决策

| 决策项 | 结论 |
|---|---|
| 输入格式 | pcap 文件（标准抓包文件，tcpdump -w 和 Wireshark 都能生成） |
| 产品形态 | Web 页面（本地起服务，浏览器看可视化报告） |
| 分析场景 | 接口慢/超时排查、网络质量诊断、流量概览/谁在说话（三个都做，分层递进） |

## 四、技术架构

Node 后端负责解析分析，前端纯展示：

```
┌─ 前端 (Vite + Vue/React)
│   上传 pcap → 展示报告：概览卡片 / 时序图 / 连接列表
│
├─ 后端 (Node + TS)
│   ├─ pcap 文件解析（格式简单，可手写或用 pcap-parser）
│   ├─ TCP 会话重组：按四元组分流，追踪 seq/ack
│   ├─ 指标计算层：RTT估算 / 重传检测 / 连接状态机
│   └─ 诊断规则层：把指标翻译成"人话结论" ← 核心差异化
│
└─ 产物：结构化 JSON 报告，前端渲染
```

说明：三个场景共享同一套解析底座（pcap 解析 → 包流 → TCP 会话重组），分层递进，不是三倍工作量。

## 五、分阶段实施计划

每阶段结束都是可用状态：

| 阶段 | 内容 | 价值验证点 |
|---|---|---|
| P0 | pcap 解析 + 流量概览（TopN、协议分布、时序图） | 能跑通、页面能看 |
| P1 | TCP 会话重组 + 网络质量（重传/RTT/RST 高亮） | 能发现"网络抖动"类问题 |
| P2 | HTTP 明文请求耗时分解（DNS/建连/首包/传输） | 能回答"接口为什么慢" |

工作量预估（业余时间计）：P0 约 2-3 天，P1 / P2 各约 3-5 天。

## 六、风险与应对

| 风险 | 说明 | 应对 |
|---|---|---|
| TLS 普及 | 现在流量基本是 HTTPS，载荷读不到 | 只做时序/连接行为分析，聚焦"网络行为诊断"而非"内容分析" |
| 协议解析无底洞 | TCP 乱序、分片、OoO 等边缘 case 很多 | MVP 必须砍掉；P1 参考成熟实现（对照 tshark 的 tcp analysis 校验正确性） |
| 大文件性能 | 几百 MB 的 pcap | 流式解析 + 前端分页/聚合，不要一次全渲染 |
| 竞品 | tshark+脚本、pyshark 能凑合用 | 竞品没有"小白友好"成品，机会仍在 |
| 测试数据 | 需要典型 pcap 做验收基准 | 提前准备几个典型样本：正常、慢接口、网络抖动 |
