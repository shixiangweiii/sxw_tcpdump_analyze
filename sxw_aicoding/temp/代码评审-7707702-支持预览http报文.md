## 总体评价

整体架构清晰：嗅探（`sniffAppProtocol`）→ 按协议决定载荷保留（`retainPayload`）→ 双方向流重组（`reassemble`）→ HTTP 解析（`decode/http.ts`）→ 事务与耗时（`http-analysis.ts`）→ 映射回每个 TCP 包（`AppSpan`/`appNote`）→ 前端卡片与梯形图联动。分层合理，防御性细节（解析防死循环、`payload.slice()` 防内存钉住、空洞用 0 填充且不冒充真实数据）做得扎实，真实抓包逐字节核对的回归测试质量很高。

以下问题按严重程度排列。

## 一、中等问题（建议优先排期修复）

### 1. Redis/memcached 文本协议会被误判成 HTTP，并产出编造的报文

- **位置**：`packages/core/src/decode/http.ts:66-73`（`looksLikeRequestLine`）、`packages/core/src/decode/http.ts:176-197`（头部没收全分支）、`packages/core/src/analyze/connections.ts:317`、`packages/core/src/analyze/connections.ts:488-491`
- **现象**：`looksLikeRequestLine` 只看「大写方法 + 空格」前缀。Redis 读命令 `GET key\r\n` 完全命中，连接被嗅探定为 `http1`。随后流里找不到 `\r\n\r\n`，走「头部没收全」分支，产出一条 startLine 为 `GET key`、`httpVersion` 被 `emptyShape` 默认填成 `HTTP/1.1`（编造值）的“不完整 HTTP 请求”。
- **后果**：`materialize` 只有在「一条消息都解不出来」时才回退 `unknown`，这里解出了 1 条，于是界面显示 `GET key · 无响应` 的假 HTTP 结论——与 README「自动给结论的前提是结论正确」的定位直接冲突，对小白用户的伤害比不显示更大。
- **修复思路（供参考）**：头部没收全分支不要默认填 `HTTP/1.1`；或对请求行额外校验行尾存在 `HTTP/\d` 版本 token 再认定 HTTP。

### 2. 事务 note 与耗时条在「服务端处理 ≤ 0」时互相矛盾，且内网场景很常见

- **位置**：`packages/core/src/analyze/http-analysis.ts:348-353`（`describeTransaction`）、`packages/web/src/components/HttpTransactions.tsx:109`（`TimingBar`）
- **现象**：note 里 `think > 0` 才写「服务端处理 X」，否则因 else-if 结构连「等首字节」也不写，note 完全不提耗时；而前端用 `Math.max(0, ttfb - acked)`，会渲染一段「服务端处理 0μs」。
- **触发频率**：不是边角案例。内网快速链路 + 延迟 ACK 下，服务端把对请求的 ACK 捎在响应首包上（piggyback），`acked === ttfb`、`think === 0` 是常态——恰恰是本工具的主场景。
- **修复思路**：两端统一口径——`think <= 0` 时 note 与耗时条都明确写「网络太快，服务端处理时间无法从 ACK 中区分」或都按 0 处理。

### 3. 内存模型被本次提交实质性改变，README 的承诺需要更新口径

- **位置**：`packages/core/src/analyze/connections.ts:26-29`（`SNIFF_BUDGET = 32KB`/方向、`HTTP_RETAIN_CAP = 1MB`/连接）、`packages/server/src/session-store.ts`（LRU 8 会话全量持有结果）
- **现象**：「载荷即用即弃」改为「HTTP 连接每条最多留 1MB + 未决连接每方向 32KB」。「内存与文件大小无关」仍成立，但常数从 0 变成每连接 MB 级；正文 `text` 每消息最多再留 256KB（`BODY_TEXT_CAP`）。
- **后果**：千条 HTTP 连接的抓包，最坏情况单会话 GB 级，×8 个 LRU 会话放大。当前内网小抓包没问题，但缺少总量兜底。
- **修复思路**：增加跨连接的全局保留预算；同时更新 README 中「内存占用与连接数相关」的量级描述。

### 4. `clientStreamComplete` 不覆盖「流前缀缺失」

- **位置**：`packages/core/src/analyze/reassemble.ts:120-123`（gaps 只记内部空洞）、`packages/core/src/analyze/http-analysis.ts:86`
- **现象**：若抓包恰好丢了连接最前面的数据包（`base > 1` 且后面无洞），`gaps` 为空 → HTTP quality 判流完整；而 `startsAtStreamBeginning` 已经算出了这个事实，却没有并入 quality。此时解析走 `findMessageStart`，首条消息若被截成无签名前缀会静默丢失且无质量提示。
- **缓解现状**：anomaly 层的 lost-segment 能部分兜底，但 HTTP 层自相矛盾。
- **修复思路**：`clientStreamComplete` / `serverStreamComplete` 的判定并入 `!startsAtStreamBeginning` 的情况，或在 `HttpQuality` 中单独暴露该标志。

## 二、低危 / 边界问题

| # | 位置 | 问题 |
|---|---|---|
| 1 | `http-analysis.ts:317-323` | 找请求 ACK 用 `packets.find`（抓包序第一个满足者）。`tcpdump -i any` 多接口时间戳可能轻微乱序，会取到非最早的合格 ACK，使 `requestAckedMicros` 偏大。取「满足条件中 tsMicros 最小」更稳 |
| 2 | `http.ts:311-332` | 请求没抓到时（`requestMethods[i]` 为 `''`），HEAD 响应会按 Content-Length 吞掉后续字节导致解析错位。线路上本就歧义，建议至少在注解中提示 |
| 3 | `http.ts:563-570` | 头部结束只认 CRLFCRLF，LF-only 换行的非规范服务器整条消息会判「头部没收全」（Wireshark 容忍 LF） |
| 4 | `http.ts:477-512`（`buildBody`） | 只检查 `Content-Encoding`；`Transfer-Encoding: gzip, chunked`（TE 层压缩）解块后会被当文本解出乱码 |
| 5 | `HttpTransactions.tsx:158` | 头部的 React key 用 `name:value`，两条同名同值的 Set-Cookie 会撞 key |
| 6 | `http.ts:276`（`unfold`） | `out.length > 1` 应为 `>= 1`：紧跟起始行的折叠行不会被折（实际影响几乎为零） |

## 三、命名与实际逻辑的一致性问题

1. **同一概念三层三个名字**：`connections.ts` 的 `clientFin/serverFin` → `http-analysis.ts` 的 `clientClosed/serverClosed` → `decode/http.ts` 的 `closedCleanly`。其中 `closedCleanly` 名不副实——注释和实现都是「看到 FIN」，FIN 不等于“干净关闭”（RST 也收尾）。建议统一为 `sawFin` 一类。
2. **`clientClosed` 是事实上的死输入**：`decideFraming`（`http.ts:331`）对请求方向永远不返回 `until-close`，所以传给 `parseRequests` 的 `closedCleanly` 从不生效。API 面积大于实际行为，容易误导读者以为请求也支持「读到关闭」。
3. **`AppSpan.part = 'start-line'`** 实际语义是「该包承载消息开头（可能包含整个头部区）」，`'headers'` 是「不含开头的头部延续」；且 `LadderDiagram` 的 `badgeContent` 对 `'headers'` 也显示「…续」徽章，视觉上暗示的是正文延续。命名与展示双重歧义。
4. **「第 X~Y 个字符」是 0 基半开区间**（`http-analysis.ts:397`，README 示例「第 1399~2797 个字符」）：按“第 N 个字符”的自然读法会差一位。对小白用户建议改成 1 基闭区间或明确写偏移量。
5. **两个语义不同的 unknown**：`sniffAppProtocol` 返回 `null` 表示「还没看出来」，`AppProtocol = 'unknown'` 表示「已放弃」。跨层阅读时容易混淆。
6. **`HttpMessage.firstPacketIndex`** 名字容易被读成「抓包序里的第一个包」，实际是「流序上承载首字节的那个包的全局序号」——注释已说明，命名本身有误导空间。

## 四、做得好的设计（保持）

- 空洞用 0 填充配合 `touchesGap`，保证偏移对齐的同时不让填充值冒充真实数据。
- `payload.slice()` 防止 subarray 引用把整份 pcap 文件钉在内存里。
- TTFB 按流序取首包（真实抓包里服务端第一个到达的包承载的是正文中段），并用真实抓包回归锁死该行为。
- 列表接口剥掉 `packets` 与 `http` 字段，防止大连接把列表响应撑爆；详情按需加载。
- 真实抓包（www.chinakids.net）逐字节核对的回归测试，覆盖乱序、重传、chunked、无 charset 头等现实组合。

## 五、修复优先级建议

1. **高**：问题一.1（协议误判出假结论）、一.2（note 与耗时条矛盾，内网主场景常触发）——与「给小白正确结论」的产品定位直接相关。
2. **中**：一.3（内存总量兜底 + README 口径）、一.4（流前缀缺失的质量标注）。
3. **低**：第二章边界问题与第三章命名项，可随下次重构顺手统一。
